# 校园成绩：第一轮术语召回评测

这轮只回答：用户提问后，项目是否找到了应该提供给大模型的术语？不生成 SQL，不调用聊天模型，不查询学生记录。

## 现在从这里开始

在 PowerShell 中执行：

```powershell
cd D:\SQLBot-main
python tools/campus_recall/evaluate.py --mode check
```

看到 `CHECK ONLY` 和 `Report:` 表示测试题校验和本地词语匹配演示完成。打开输出路径里的 `report.md`，先看 Q01、Q13、Q17：

1. Q01 明确说“曾不及格”，词语匹配就能找到。
2. Q13 说“以前有课没考过，后来通过的也算”，没有直接使用术语或别名，词语匹配找不到。
3. Q17 同时提“曾不及格”和“尚不及格”，应该找到两个术语。

**check 模式的分数不是 SQLBot 的真实召回效果，也不是 embedding 效果。** 它帮助你理解测试题和报告。真实结果必须运行 live。

## 数据从哪里来

来源是 `项目学习文档/学情分析数据样本` 下已有的四份 .xls。只读取了各表前两行的标题、表头和表尺寸；没有复制学生姓名、学号或成绩记录到测试集。

| 文件 | 本轮用到的结构 |
|---|---|
| 2404学生成绩明细.xls | 总成绩、考试时间、学分、修读方式、课程属性、班级等 |
| 2404加权排名.xls.xls | GPA、加权学分成绩、平均成绩、要求总学分、已修课程学分等 |
| 2404曾不及格.xls.xls | 历史不及格课程信息，含学年学期、课程成绩等 |
| 2404尚不及格.xls | 当前未通过课程信息，含成绩、不及格次数等 |

`fixture.json` 包含 8 个术语、别名、解释，以及 24 个问题的预期答案。字段解释是本实验约定，不能当作已核实的学校业务规范。GPA 和加权成绩使用现有报表字段，不猜换算公式。后续评测 SQL 前，还需核实考试记录粒度、补考重修、课程通过规则。

第一轮只是术语检索，不需要先导入全部成绩明细。下一轮表/字段召回才需要连接成绩数据源。

## 源码究竟做了什么

入口：`backend/apps/terminology/curd/terminology.py` 的 `select_terminology_by_word`。

1. PostgreSQL 用 `ILIKE` 判断问题是否包含术语名称或别名。
2. `EmbeddingModelCache.get_model().embed_query(word)` 将完整问题向量化；此处没有问题切片。
3. 使用 pgvector 的余弦距离，按相似度阈值和 Top K 检索。
4. 合并两路结果，将别名归并到主术语，取出术语解释。

入库方法 `save_embeddings` 只对每条记录的 `word` 做 embedding；术语解释没有参与向量化。别名也是独立向量记录，因此多个别名可能占用向量 Top K 名额。

当前源码默认相似度严格大于 0.4、向量 Top K 为 5，运行环境可以覆盖配置。最终集合还包含词语匹配结果，既不保证只有 5 项，也没有统一相似度排序。

## 如何接上真实召回

需要：SQLBot 的 Python 3.11 后端环境、已初始化的应用 PostgreSQL 数据库、项目本地 embedding 模型。普通 Python 3.14 环境不能直接运行 live。

1. 启动你的 SQLBot 测试实例。先确认实际部署方式；不要为了运行此脚本覆盖现有配置。
2. 用工作空间管理员进入“专业术语”页面。前端实现位于 `frontend/src/views/system/professional/index.vue`。
3. 使用专门的测试工作空间。在该测试范围只配置 `fixture.json` 的 8 个主术语，别名填到对应主术语下，解释原样复制并启用。字段对应：`word` 是术语名称，`other_words` 是别名，`description` 是解释。
4. 若使用专用成绩数据源，将这 8 个术语关联该数据源；注意全局术语也会参与召回。不要删除其他业务的术语，应换用干净测试工作空间。
5. 等待后台术语向量生成完成。脚本会检查名称、别名所属主词、解释、启用状态和向量是否存在。
6. 确认测试工作空间 ID（oid），不要照抄默认 1。可由管理员在数据库工具只读查询 `SELECT DISTINCT oid FROM terminology;` 查看候选，再按已创建的测试术语确认归属。
7. 在**这份源码对应的后端 Python 3.11 环境**执行下面命令。将 `<测试工作空间ID>` 换成实际数字；它是占位符，不能原样执行。

```text
python tools/campus_recall/evaluate.py --mode live --oid <测试工作空间ID>
```

指定数据源时，再添加 `--datasource <测试数据源ID>`。本轮不支持高级应用范围。

脚本会切换到 backend 目录，因此 `.env` 读取位置与源码配置一致。源码默认本地模型目录为 `/opt/sqlbot/models`；Windows 本地运行需让 `LOCAL_MODEL_PATH` 指向真实模型父目录，包含 `embedding/shibing624_text2vec-base-chinese`。不要填写一个不存在的目录。

如果部署在 Docker/服务器，脚本需要在能够导入这份 backend 源码并连接其数据库的环境中运行，不能只把 evaluate.py 单文件放进任意容器。应先确认实例、源码路径和 Python 路径，再给出对应命令。

live 直接调用原函数，依次运行 `source_lexical`（关闭向量分支）与 `source_hybrid`（原来的混合召回）。开关只影响评测进程，不修改配置文件或正在运行的服务；数据库事务强制只读，不创建术语。

模型无法加载、语料不一致、向量为空，或原函数吞掉向量异常时，脚本报错退出，不输出看似正常的实测报告。检查目录中报告的时间戳，避免误读上次报告。

## 报告怎么看

每次生成单独的 `reports/<模式>-<时间>/report.md` 和 `report.json`。JSON 包含逐题耗时、分类指标、语料和源码哈希、模型名称、阈值等信息。耗时只是本轮观测，不是性能基准。

| 指标 | 含义 |
|---|---|
| recall | 每道有答案题的命中术语数 / 应命中数，再对这些题取平均 |
| precision | 返回术语中正确的比例，再对非空返回或有预期答案的题取平均；正例无返回记 0 |
| all_hit | 有答案题里，应命中术语全部找到的题目比例；多召回仍可能通过此项 |
| exact_match | 所有题里，实际集合与预期集合完全一致的比例 |
| false_positive | 无答案题里仍返回术语的比例；没有无答案题时为 null |

这些都是最终集合指标，**不是 Recall@K**。无答案题不参与 recall、all_hit 的分母。

重点看 JSON 的 `by_category.semantic`：向量是否补回 Q13～Q16？再看 `negative`：是否给天气、食堂等问题硬塞了术语？最后看 `multi` 是否漏了第二个指标。

不要只追求召回率变高：阈值降低后可能找回更多术语，也带来更多错误术语。初轮 24 题是学习用开发集，不能作为简历里的泛化结论。后续扩充并独立保留测试集，固定语料、模型和题集，每次只改变一个因素。

## 验证评测程序

```powershell
python -m unittest discover -s tools/campus_recall -p test_evaluate.py -v
```

覆盖多指标部分命中、重复结果去重、误召回、负例分母，以及语义题确实无法被简单词语匹配命中。这些测试通过只证明指标与测试集基本正确，不能代替 live 验证。
