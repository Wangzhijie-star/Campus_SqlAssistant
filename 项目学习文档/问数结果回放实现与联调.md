更新日期：2026-09-14。本次代码更新位于 `D:/SQLBot-main`。Ubuntu 运行副本尚未同步，业务数据库尚未迁移；完成源码同步与迁移后才能进行页面联调。

## 1. 本次确定的行为

| 查询情况 | 响应 | 是否调用 AI |
| --- | --- | --- |
| 请求占位仍被占用 | HTTP 409，`PROCESSING` | 不调用，原任务继续 |
| 取得请求占位，数据库记录仍未完成 | HTTP 409，`RESULT_UNAVAILABLE`，本次执行未获得完整结果，请重新提问 | 不调用，不修改旧记录 |
| 已保存 `SUCCESS` | HTTP 200，JSON 回放 | 不调用 |
| 已保存 `FAILED` | HTTP 200，JSON 回放，业务状态仍为失败 | 不调用 |
| 没有记录，但会话忙 | HTTP 409，`CHAT_BUSY`，释放本次请求占位 | 不调用 |
| 没有记录且取得会话锁 | 复核后创建问答记录并执行 | 调用 |
| 同 ID 的原始内容或调用选项发生变化 | HTTP 409，`REQUEST_ID_CONFLICT` | 不调用 |
| Redis 读取或获取锁异常 | HTTP 503，`COORDINATION_UNAVAILABLE` | 不无保护地执行 |

没有新增“状态待确认”。遗留的 `PROCESSING` 不自动改为失败，不自动重跑，也不扫描操作日志判断执行到了哪一步。用户重新提问使用新 request_id，仍需经过会话锁。

这里结束的是当前重试请求，不能将其解释为强制杀掉旧线程。旧任务继续受租约检查保护。当前保护不是数据库 fencing，不能宣称严格 exactly-once。

## 2. 数据变更

在 `chat_record` 新增三个可空字段，历史记录保持空值，不猜测或补造历史请求 ID：

| 字段 | 用途 |
| --- | --- |
| request_id，最长 128 字符 | 请求与问答记录的关联 |
| request_fingerprint，64 字符 | 校验同一个 ID 是否对应同一原始提问、调用选项和用户 |
| status，最长 16 字符 | PROCESSING、SUCCESS、FAILED |

唯一约束 `uq_chat_record_request(chat_id, request_id)` 防止同一请求建立多条记录。PostgreSQL 默认唯一约束允许多条历史 NULL request_id 记录。

fingerprint 是内容一致性检查，不是用来生成 request_id 的种子。它在重新生成命令被改写之前计算。状态与旧 finish 字段分开：finish=true 可以来自报错，只有后台任务完成后的收尾逻辑才能发布本次请求终态。

## 3. 入口调用链

入口：[chat.py](D:/SQLBot-main/backend/apps/chat/api/chat.py) 的 `guarded_question()`。

```text
权限校验
  → fingerprint()：保留原始提问语义
  → cached_result()：查 Redis，并轻量核对原记录仍存在、终态和指纹
      → 命中：直接返回 JSON
      → 未命中：gate.enter(request_only=True)
          → database_result()
              → 终态：snapshot() → cache_result() → 返回 JSON
              → 未完成：RESULT_UNAVAILABLE → 释放本次占位
              → 不存在：gate.acquire_chat()
                  → 再查 database_result()
                  → 给 lease 绑定请求信息和 on_completed 回调
                  → question_answer_inner() → 原有执行链路
```

缓存命中时的数据库核对只取 ID、状态和指纹，不重新读取图表或聚合日志，用来避免回放已删除记录。回放仍先经过会话权限校验。

## 4. 两阶段锁如何工作

[question_gate.py](D:/SQLBot-main/backend/common/core/question_gate.py) 保留原有默认 `enter()` 行为，新增 `request_only=True`，供回放入口先取得请求占位。

需要执行时调用 `acquire_chat()`，将请求租约升级为持有两把锁。升级时暂停续期任务，避免续期脚本检查到尚未取得的会话键；成功后对两把锁验证续期，再恢复定时任务。失败仍通过原来的 token 校验清理，不删除其他持有者的锁。

读取终态不需要会话锁。请求未提交到后台时，由入口 finally 清理；已经提交则由 Future 观察任务负责。

## 5. 记录创建与任务结束

[chat.py（记录存储）](D:/SQLBot-main/backend/apps/chat/curd/chat.py) 的 `save_question()` 把 lease 中的 request_id、指纹和 PROCESSING 写入记录，提交后将 record_id 关联回 lease。带请求 ID 的分析或预测命令所创建的记录采用相同关联；没有请求 ID 的原有独立分析、预测入口保持原行为。

后台任务 Future 完成后，`QuestionLease._observe()` 调用 `on_completed()`：

```text
complete_result()
  → 在线程中执行 finalize()
      → 检查 lease 仍有效
      → 有执行失败标志、有保存的 error，或未完成：FAILED
      → 正常完成且无错误：SUCCESS
      → 提交数据库
  → 在线程中执行 snapshot()
  → 在 asyncio 事件循环中 cache_result()
  → finally 停止续期并按 token 释放锁
```

任务提交失败但已创建记录时，入口也会尝试保存一份明确失败结果。进程强杀、数据库不可用或租约丢失仍可能留下 PROCESSING；后续请求走 RESULT_UNAVAILABLE，不推断失败原因。

数据库终态提交成功而快照组装或 Redis 写入失败，不撤销终态。锁释放仍执行；下次可以再次从数据库组装回放。

## 6. 回放快照与前端

实现：[question_replay.py](D:/SQLBot-main/backend/apps/chat/curd/question_replay.py)。

缓存键：`{prefix}:request:replay:{chat_id}:{request_id}`。缓存寿命为 600 秒，定义在 `REPLAY_TTL`。过期后依赖数据库关联，不把缓存寿命当成幂等保留时间。

JSON 包含 replay、chat_id、request_id、record_id、status 和 record 展示对象。record 使用已有 `ChatRecordResult` 和 `format_record()` 格式，包括已存储的 SQL、图表、绘图数据、错误、时间及 token 汇总。不会执行一次新的 SQL 查询来刷新业务数据。

生成快照会读取原记录的 ChatLog 汇总 token，但不会将整份执行详情放进 Redis。Redis 回填后直接返回已组装的 JSON，不再读一次缓存。

[ChartAnswer.vue](D:/SQLBot-main/frontend/src/views/chat/answer/ChartAnswer.vue) 按 Content-Type 区分 SSE 与 JSON，并兼容全局响应中间件的 data 包装。JSON 回放按 record.id 合并，移除重复的临时占位记录。

[index.vue](D:/SQLBot-main/frontend/src/views/chat/index.vue) 的完成回调接受 replay 标记。回放不重新获取 token，也不自动请求推荐问题，避免额外模型调用。RESULT_UNAVAILABLE 显示提示，并在输入框为空时恢复原问题，供用户主动重新提交。

首次调用保留原有 SSE 或 MCP 响应；重复调用得到回放 JSON。外部调用方需要识别 replay/status/record 这个回放契约，不能只按首次响应格式解析。

## 8. 联调验收

### 执行太快时：开启临时暂停

新增 `SQLBOT_TEST_PAUSE_SECONDS` 进程环境变量，默认 0，范围 0～120 秒。仅在新请求已取得请求锁和会话锁、数据库复核无记录之后暂停。使用 `await asyncio.sleep()`，事件循环和租约续期继续运行；回放与重复拒绝分支不暂停。暂停结束后再次校验租约，失效则拒绝推进。

暂停发生在创建问答记录和调用模型之前，因此这段时间数据库还没有新记录，是预期行为。每个新请求都会暂停，并非只暂停一次。它用于验收，不用于正常运行。

对已同步 prepared-20260914-180351 的 Ubuntu 副本，停止后端后执行下面的安装脚本；它仅更新两个文件，检查副本没有额外改动，并备份原文件：

```bash
python3 /mnt/d/SQLBot-main/tools/request_id_sync/install_test_pause.py
cd /home/sqlbotdev/sqlbot-local/backend
source .venv/bin/activate
SQLBOT_TEST_PAUSE_SECONDS=120 uvicorn main:app --host 127.0.0.1 --port 8000
```

新请求进入时，后端输出 `Acceptance test pause: holding request/chat locks ...`。在 120 秒内复制并重发原请求，预期 409 PROCESSING；换 request_id 后发送同会话请求，预期 409 CHAT_BUSY。不要重发已完成的旧请求来测试暂停，因为旧请求会直接回放。

测试结束后 Ctrl+C 停止后端，用不带该变量的原启动命令重启。上述行内环境变量仅作用于这次进程，不需要修改 .env、前端或数据库。

### 正常验收用例

1. 发起新问题，记录 Network 中的 chat_id 和 request_id，等待任务完成。
2. 用同一身份、同一入口、完全相同的请求体重发。预期得到 replay=true 的 JSON，record_id 不变，数据库不增加一条记录。
3. 对已明确失败的请求重发，预期回放同一失败原因，不新增模型调用。
4. 等待缓存十分钟过期再重发，预期数据库回查后重建缓存。
5. 在隔离测试会话中模拟一条关联同 ID 的 PROCESSING 记录，且没有该请求占位锁，再重发。预期 RESULT_UNAVAILABLE；不返回残缺图表、不改旧状态、不创建新记录。
6. 原任务正常执行时重发，预期 PROCESSING；另一 ID 提问同一会话时预期 CHAT_BUSY。
7. 页面收到 RESULT_UNAVAILABLE 后，用户重新点击发送，确认新 request_id 与上次不同。
8. 会话正在执行另一个问题时重发已完成请求，仍能回放。

不要在真实用户任务仍运行时删除锁来模拟故障。自动测试使用隔离存储验证这类分支。
