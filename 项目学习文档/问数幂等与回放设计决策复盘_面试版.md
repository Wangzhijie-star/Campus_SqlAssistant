## 1. 出发点：减少重复推进，而不是先堆中间件

你的维护方向包括幂等、熔断、降级、人工兜底、上下文治理、记忆和安全审计。第一步选择幂等，是因为重复问数可能重复调用模型、重复查询并产生重复记录，还会增加用户理解结果的难度。未来 Java 教学平台接入后，也不能只依赖当前网页的交互限制。

你持续要求“一点一点抠细节”，因此实施顺序被收敛为：先打通 request_id，再连接 Redis，再实现执行期间的两把锁，最后设计持久化结果与回放。这样每一步都有可验证的边界。

面试可以强调：我先拆分“这是不是同一次操作”和“这个会话现在能否推进”，再选择存储和锁，而不是把接入 Redis 本身当作目标。

## 2. 为什么借鉴 AI-meeting，却不能直接复制

AI-meeting 的答题链路提供了请求去重、业务推进保护和兜底的思路。但 SQLBot 有普通提问、重新生成、图表、分析等入口，业务对象和生命周期不同。

尤其是 SQLBot 的 record_id 由后端创建，不能天然作为前端第一次发送请求前就拥有的标识。重新生成也意味着：针对同一个历史结果，用户可以合法发起另一次模型调用。

我们借鉴的是分层保护的思想。不能因为另一个系统存在题级锁，就机械地给 SQLBot 添加同名的一层锁；必须先明确它保护哪个业务对象。本项目当前先保护请求和会话，不再额外为每次 AI 调用增加一把无明确边界的锁。

## 3. 第一处关键澄清：request_id 到底有什么用

你多次追问：“每次 request_id 都不同，不都能拿到锁吗？”这个疑问推动我们明确了前端协议。

| 标识 | 标识的对象 | 不承担的职责 |
| --- | --- | --- |
| chat_id | 一次会话 | 无法区分会话内的多次提问 |
| record_id | 一条后端问答记录 | 不能代替首次发出请求时的操作标识 |
| request_id | 一次用户操作及其网络重试 | 无法单独阻止另一条新请求并发进入同一会话 |
| owner_token | 本次锁持有者 | 不是业务请求 ID，也不是登录令牌 |

最后对齐的规则是：用户发起一次新操作时生成 request_id；这次操作因断网等原因重发时复用它；用户主动再次提问或重新生成时使用新 ID。

例如，R1 的第一次发送和网络重试都使用 R1。用户看完结果后点击重新生成，则使用 R2。若客户端把每次重试都换成新 ID，请求级幂等就无法把它识别为同一次操作。

**当前实现：**前端生成并保存操作 ID，后端接收、校验并传递，响应携带该 ID。后端拒绝缺失或空白值。尚未因此自动获得网络重试功能；将来添加重试代码时仍须遵守复用规则。

## 4. 为什么暂时放弃种子兜底

最初考虑过：没有 request_id 时，用 chat_id、问题内容和某个 record_id 生成稳定 ID。你进一步指出，相同参数会得到相同种子，而同一问题可能是用户有意再次提出的。

讨论过的普通提问种子是 `chat_id + base_record_id + question`，重新生成种子是 `chat_id + target_record_id + instruction`。但 base_record_id 从哪里获取、重试期间会话变化如何处理、连续两次有意重新生成如何区分，都需要额外协议。

你的决定是：先不做种子。用明确的客户端 request_id 协议和后端空值校验完成第一阶段。

这个取舍的价值在于，没有把“文本一样”误当成“业务操作一样”。代价是调用方必须升级并正确传参。

## 5. 为什么从前端限制发展成两把锁

你最初提出在前端发送后禁用输入，这能够减少普通用户重复点击。但多标签页、脚本和未来 Java 调用方都可以绕过当前页面限制，所以最终接受了后端会话互斥。

| 保护层 | 逻辑范围 | 解决的问题 |
| --- | --- | --- |
| 请求占位锁 | chat_id + request_id | 同一次操作的重复请求不能同时执行 |
| 会话锁 | chat_id | 不同 request_id 也不能同时推进同一会话 |

实际键名还带环境前缀。你认为 chat_id 在当前数据库内唯一，不必为了唯一性再加入 oid，这一判断适用于当前命名空间。权限校验仍然必须执行，不能把键的唯一性当成访问授权。如果未来多个独立数据库共用 Redis，应通过部署或数据库命名空间避免 ID 碰撞。

请求锁挡住 R1 的重试，会话锁挡住 R1 尚未结束时进入的 R2。只有请求占位成功，不能认定整个业务已经获准执行。

## 6. 为什么选择快速拒绝，而不是等待会话锁

你指出：R2 已取得自己的请求占位，但会话仍被 R1 使用。如果让 R2 一直等，网页体验不明确，Java 调用端也可能长时间占用连接和执行资源。

因此当前选择：会话锁获取失败时，立即释放 R2 自己的占位，返回明确的 CHAT_BUSY，不排队、不后台偷偷重试。

| 情形 | 当前处理 | 原任务是否继续 |
| --- | --- | --- |
| 同一请求占位失败 | PROCESSING，告知正在处理 | 继续 |
| 新请求占位成功、会话锁失败 | CHAT_BUSY，释放本次占位 | 继续 |
| 两把锁均成功 | 进入执行链路 | 执行本次任务 |

“正在处理”是本次重复调用被拒绝的原因，不是将原来的业务结果标记为 FAILED。客户端应展示可理解的提示，而不是把非成功响应当作空白结果。

## 7. 为什么用 Redis，而不是说 PostgreSQL 太慢

你希望锁机制采用 Redis，也考虑到自己的学习路线和面试表达。技术上，它适合承载跨进程共享的短期占位、过期时间和续期信息。

但这里没有性能实验能够证明 PostgreSQL 无法承担锁，也不能把其他 Java 项目里对 MySQL 的判断直接套过来。SQLBot 已有启动阶段的 PostgreSQL advisory lock；它与长时间问数的请求门禁是不同场景。

当前职责划分是：Redis 管执行期间的互斥，并计划保存短期回放快照；PostgreSQL 保存问答业务记录，并计划承担缓存未命中后的结果依据。

代价是增加了 Redis 连接、故障和租约丢失的处理。Redis 不可用时不能把异常当成“没有锁”，继续无保护地执行。

## 8. SET NX 与看门狗不是二选一

你的问题是“采用 setnx 还是看门狗”。随后明确：原子获取锁和持锁期间续期属于两个阶段。

当前使用 `SET key token NX PX ttl` 获取带过期时间的锁，取得两把锁后用 asyncio 后台任务定期续期。它是项目自己实现的租约续期机制，不是直接接入 Java 的 Redisson。

当前开发默认值为：租约 60 秒、每 20 秒续期、任务推进时限 600 秒。这些不是根据生产 P99 测出的结论。以后应参考实际问数耗时、模型调用尾延迟、事件循环延迟、Redis 往返耗时和异常恢复时间进行调整。

租约表示“在这段有效时间内拥有执行资格”。600 秒的限制是协作式检查，不能强制中断已经进入的同步模型调用，也不等于外部服务请求超时。

## 9. 为什么 token 和 Lua 必不可少

你追问创建锁时是否使用了 token。这里引入的 owner_token 用来证明“现在的锁还是我取得的那一把”。即使 request_id 相同，两次获取尝试的持有者 token 也应不同。

典型竞态：旧任务停顿导致锁过期，新任务取得同名锁；旧任务恢复后如果直接 DEL，就会删掉新任务的锁。续期也不能把新持有者的租约误认为自己的。

因此释放时原子执行“比对 token，再删除”；续期时原子执行“确认两把锁的 token 都匹配，再延长有效期”。Lua 将检查和修改放在 Redis 内一次执行，避免客户端先 GET 再 DEL/PEXPIRE 中间发生竞争。

当前续期任务使用 Python asyncio；实际问数包含线程池工作，不能让阻塞操作占住事件循环，否则续期也无法按时运行。当前实现面向单 Redis 实例，未来迁移 Redis Cluster 时需要重新检查多键脚本的同槽要求。

## 10. 你的 finally 要求，如何变成执行生命周期管理

你明确要求：无论正常结束还是异常，都要有 finally 兜底释放。这推动实现进一步区分了三个结束时刻：接口返回、浏览器连接结束、后台执行结束。

SSE 接口返回 StreamingResponse 时，线程可能还在调用模型；浏览器断开时，线程也未必停止。如果在这两个时刻直接释放，就可能允许另一个请求与旧线程同时执行。

当前处理为：任务提交前失败，由入口清理；提交成功后，由独立观察任务跟随线程池 Future，确认实际工作完成后进入清理。清理先停止续期，再按 token 释放锁。释放失败由 TTL 兜底，进程被强制终止时也依赖 TTL，而不能指望 finally 必然执行。

租约失效后，执行链路在检查点停止后续推进。但检查点不是数据库写入的原子 fencing，不能据此宣称任何故障下都不存在旧线程晚写。

## 11. 为什么回放选择“可展示结果”，而不是只缓存 record_id

你的重点是会话框体验：图表、原来的 token 消耗和耗时要快速呈现；执行详情只在用户点击时查询。

因此回放计划保存可直接展示的 JSON 快照，包括关联 record_id、图表配置和绘图数据、展示所需 SQL 或文字、原始 token 与耗时，以及终态错误信息。具体字段还需与当前前端消费字段对齐，不能只缓存一个图表图标。

执行详情继续按需从数据库读取，避免把全部过程日志塞进 Redis。首次生成继续 SSE，回放可直接 JSON；前端需要识别两类响应，并按 record_id 避免重复插入同一条结果。数据瞬时返回本身不是主要问题，响应契约一致才是关键。

**这是已讨论的回放方向，尚未完成实现。**token 与耗时涉及现有日志聚合，不能假设都已是 chat_record 的直接字段。回放使用保存的数据，不重新执行 SQL，也不应把原 token 数量算成一次新的模型消耗。

## 12. 你提出十分钟缓存和数据库兜底

你的建议是缓存有效期先定十分钟，同时考虑 Redis 写入失败：下次查不到缓存时，不能直接认定是新请求并再次调用模型。

因此目标逻辑增加数据库回查：取得请求占位后，通过 chat_id + request_id 查原记录；若已有终态，就从持久化数据组装回放结果，并尝试回填 Redis。

你原先提出“回填后再读 Redis”。实现上可以直接返回刚组装的同一份 JSON，不必多一次 Redis 读取；回填失败也不应丢掉已经取得的结果。

十分钟只是缓存寿命，不是业务去重只有十分钟。缓存过期后能否继续回放，取决于数据库关联记录的保留与查询能力。Redis 读取报错与正常未命中必须区分。

## 13. 你的重要修正：失败也是本次操作的结果

早期讨论容易把“成功才回放、失败再试”作为默认方向。你指出：幂等的目的是避免同一次操作重复调用 AI，失败后是否重新生成应该交给用户。

因此对齐为：已落库的成功结果可以回放；已落库、明确结束的失败结果也可以回放，包括失败原因和可展示的阶段性内容。相同 request_id 不因业务失败就自动重新调用 AI；用户主动重新生成时使用新 request_id。

这项选择使失败语义稳定，也保留用户对成本的控制。但失败快照要准确，不能把处理中或记录尚未写完误判为最终失败。

回放提升的是返回速度和结果一致性，不会提高原 SQL 的正确率，也不代表数据库当前实时数据。

## 14. 为什么讨论转向复用 chat_record

你追问额外状态表有什么用，并提出直接查询原问答记录。随后澄清：chat_record 在提问初期就创建，SQL、数据、图表等后续逐步填充，所以记录存在不等于已经完成。

现有 finish=true 也不能简单视为成功：保存错误和结束流程都可能设置它。要区分可回放成功、可回放失败和未完成记录，需要明确终态依据。

当前建议方向是优先评估扩展 chat_record：增加 request_id，建立 chat_id + request_id 的唯一关联，明确流程状态；历史记录需要兼容空 request_id。尚未将这些持久化改动落地。

两类字段职责不同：关联键回答“这是哪次请求的记录”；状态回答“这条记录能否作为最终结果返回”。独立请求台账有利于记录创建前的受理阶段和更强恢复，但会增加同步复杂度，不能只为保险就直接添加。

## 15. 仍需再确认：进程崩溃留下半条记录怎么办

这里必须保留讨论中的分歧，不能写成已经达成一致。

你倾向于：如果旧流程结束或崩溃，能记录原因就回放失败；没有可用结果时，再走流程也有实际价值。前面的建议则在“恢复执行”和“标记中断、用户重新生成”之间出现过变化。

已经确定的是：明确终态失败可以回放。尚未确定的是：只找到未完成记录时，如何证明旧执行已结束，以及同一 request_id 是否允许重新执行。

取得锁只证明当前 Redis 没有有效的冲突租约，不绝对证明旧线程已经停止。完善这一分支前，需要对齐：

1. 如何判定记录确实中断，而不是旧工作仍在执行。
2. 是否将中断保存成终态失败，让用户用新 ID 再生成。
3. 若支持同 ID 恢复，是复用记录还是增加尝试记录，如何避免重复模型调用和旧线程晚写。

当前阶段不要宣称具备故障自动恢复或严格 exactly-once。你对复杂度的控制是设计取舍，不应靠隐藏这条边界来解释。

## 16. 最后澄清：回放到底还要抢谁的锁

你最后追问：“取得占位后，如果无记录或明显终态，还要争夺谁的锁？”这里应把两个分支拆开。

| 取得请求占位后的查询结果 | 后续处理 | 是否需要会话锁 |
| --- | --- | --- |
| 已有明确成功或失败终态 | 组装回放、尝试回填、返回并释放请求占位 | 不需要 |
| 没有原记录，需要新执行 | 尝试会话锁，成功后复核并创建记录 | 需要 |
| 存在未完成记录 | 进入待确认的中断/恢复策略 | 若要恢复执行则需要，但有锁仍不够证明可安全恢复 |

所以“明显终态也要继续争夺会话锁”应予以纠正。读取旧结果不应被会话里另一条新问题挡住。需要串行的是会话推进。

目标流程可概括为：权限校验 → 查回放缓存 → 未命中则取请求占位 → 回查数据库 → 终态直接回放；需要新执行才继续取会话锁。缓存返回也必须保证权限与记录有效性。相同 ID 携带不同内容的冲突处理，以及重新生成前原始指令的指纹保存，还需细化。

实现上使用 Redis SET NX PX 获取锁，用 asyncio 定时续期，Lua 原子校验持有者 token 后续期或释放。释放绑定后台任务实际完成，而不是浏览器断开，避免后台还在运行就放行另一条请求。

下一阶段是回放。我主张成功和明确失败都作为本次操作的结果，重复请求不自动再次调用模型，是否重新生成由用户决定。计划缓存十分钟的展示快照，数据库保存关联作为缓存未命中的依据。双锁已经验证，回放和中断恢复还在设计，当前不会把它说成严格只执行一次。”

## 19. 常见追问速查

| 面试追问 | 回答要点 |
| --- | --- |
| request_id 每次不同还有什么用？ | 每次新操作不同，同一操作重试必须相同；不同操作并发由会话锁处理。 |
| 为什么不用问题文本去重？ | 文本相同可能是有意重复，操作身份不能仅凭内容判断。 |
| 为什么两把锁？ | 分别保护同请求重复进入和同会话不同请求并发。 |
| 为什么不等锁？ | 当前选择快速拒绝，减少长等待资源占用；需要排队时应另设计队列协议。 |
| 为什么不用数据库锁？ | Redis 适配当前短期租约需求；不是证明数据库锁性能不足，且需承担 Redis 故障处理成本。 |
| finally 不能保证释放吗？ | 进程强杀不会执行，需 TTL；SSE 入口结束也不是后台任务结束。 |
| 有 TTL 为什么还续期？ | 模型调用耗时变化大，短 TTL 可能过早放行，单纯长 TTL 又拖慢故障释放。 |
| 为什么必须 Lua？ | 让所有权判断与修改原子完成，避免误删或误续新持有者的锁。 |
| 缓存十分钟后还能幂等吗？ | 计划依赖数据库请求关联回查，十分钟是缓存有效期而非幂等承诺时长。 |
| 失败为什么也回放？ | 相同操作保持稳定结果，用户通过新操作明确选择是否再次调用模型。 |
| 状态是不是锁的重复保险？ | 锁记录当前执行资格；持久化状态描述已有记录是否为可回放终态，两者问题不同。 |
| 能保证 exactly-once 吗？ | 不能。租约丢失、旧工作晚写和外部调用的不确定结果仍需额外协议。 |

复习时将“我已实现”“我已决定下一步采用”“我还需验证”分开讲。最有价值的部分是你主动发现 ID 语义、会话竞争、失败回放和恢复复杂度之间的区别，并据此收敛了实施范围。
