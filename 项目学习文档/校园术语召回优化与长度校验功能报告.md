# 校园术语召回优化与长度校验功能报告

状态：第一阶段结项，2026-09-10。Ubuntu 运行副本为 `/home/sqlbotdev/sqlbot-local`。本阶段完成后端 token 长度校验，并通过新增、编辑的网页验证。按用户决定，本次迭代停在此处；批量导入现场验证、名称＋解释向量重建及参数切换不计入已完成成果。

## 本阶段交付结果

管理员新增或编辑术语时，系统在写入数据库前计算名称与解释拼接后的 token 数，同时检查每个同义词与解释的组合。任一组合超过当前模型有效上限时，整组拒绝，页面显示实际 token 数、模型上限和缩减提示。编辑被拒绝后，原解释和同义词保持原样。

该功能解决的是未来采用“名称＋解释”检索时的输入长度约束问题。当前运行副本的向量生成仍使用原来的名称文本；本阶段没有把存量向量改为名称＋解释，也没有把检索配置切换为0.65 / 3。不能将离线候选的精确率提升写成本阶段运行系统已经取得的效果。

## 项目背景

校园成绩问答需要区分历史不及格、当前未通过、成绩排名和通过率等业务含义。原系统只向量化名称及同义词，召回后才把解释加入提示词。相近术语容易同时召回，给后续 SQL 生成增加歧义。本次优化只涉及术语检索，不更改 SQL 示例和数据源检索参数。

## 前期实验及决策过程

先用“曾不及格”和“尚不及格”跑通逐题诊断，区分词语匹配和向量匹配。问题改写及同义词调整有时改善首位排名，但不能保证最终召回集合准确；部分新增同义词还引入图书馆问题的误召回。因此不能凭个别问题定参数。

扩大到26个主术语、28个同义词，共54条记录，构建200道合成题，按题族分开发集100、验证集52、测试集48。包含单术语、多术语和无关问题。标签为最具体的主术语集合，精确率只统计正例。业务标签仍需复核，多返回上级术语不必然导致错误 SQL。

在开发、验证阶段选择“名称＋解释”、阈值0.65、向量Top K 3，再运行固定候选测试集：

|方案|召回率|正例精确率|完全匹配|负例误召回|
|---|---:|---:|---:|---:|
|原系统0.4 / 5|94.4%|32.4%|2.1%|91.7%|
|名称＋解释0.65 / 3|91.7%|54.6%|39.6%|0/12|

这属于组合修改的离线结果，不能把全部收益归因于解释。测试负例只有12条，不能推断未来误召回率为零。后续修改不继续使用该测试集选参数；上线链路回放可作为工程一致性验证。

指标口径：对每个正例，召回率为命中标准术语数量除以标准术语数量，精确率为命中标准术语数量除以返回术语数量，再分别对正例求平均；正例无返回时精确率记0。完全匹配要求返回主术语集合与标准集合完全相等，统计全部题目。负例误召回率为返回非空的负例数除以负例总数。多术语全命中要求所有标准术语都出现，两方案在本次测试中均为100%，但该类样本多包含明确名称，不能代表复杂自然语言多意图的泛化能力。

长度实测：当前模型有效上限128 tokens。名称＋解释平均65.78，P95为87.35，最大138。54条中2条超限（通过率、合格率）；若截成64，则30条超限。长度包含特殊token。平均值不能替代逐条校验。

同机5轮54条批量编码P50：名称272.69ms，名称＋解释1745.6ms，64截断1440.25ms。60次问题编码P95为30.49ms。此结果不含数据库、网络、并发和大模型生成，不代表接口响应时间。文档预计算成本增加，仍不宜为约17.5%的批量耗时节约而直接截掉30条解释。

上述“名称＋解释”编码仍受模型128上限约束，2条138 tokens文本发生截断，并非所有原文均完整编码。截断存在丢失业务规则的风险，但实验尚未单独量化这2条截断对准确率的影响。因此选择保留128有效上限并在保存前逐条校验，而不是根据平均长度直接放行，也不盲目下调到64。

决策闭环为：发现名称召回混淆 → 用逐题证据区分词语和向量来源 → 扩大样本并固定候选验证 → 发现加入解释带来的长度风险 → 测量长度分布与编码成本 → 实现输入校验 → 用真实tokenizer和网页验证拒绝行为。后续召回策略切换属于下一阶段闭环，尚未完成。

## 实现设计

统一构造 `名称.strip() + '。' + 解释.strip()`，与离线实验保持一致。同义词使用自身名称及主术语解释。使用缓存中的实际模型tokenizer，在关闭截断、包含特殊token的条件下计算长度；有效上限取模型配置与tokenizer有限上限的较小值。适配器无法提供tokenizer时明确失败，不猜测上限。

新增和编辑在数据库操作前校验整个术语组；批量导入复用新增校验，超长整组失败，其余继续，错误文件保留工作表、原始行号和原因。编辑主术语和同义词改为一次数据库提交。第一阶段保留原向量生成和参数，第二阶段统一迁移后才切换，防止混用向量。

长度校验会使用已缓存的模型对象，但不执行神经网络前向推理。首次加载有成本。编码封装之后可能再次分词，仍只执行一次向量推理。当前适配依赖LangChain的 `_client`，集中在单个函数中并带显式检查，依赖升级需要回归测试。

本阶段涉及4个文件（路径相对Ubuntu项目根目录）：

|文件|修改内容|
|---|---|
|`backend/apps/terminology/embedding_validation.py`|新增统一拼接、获取tokenizer与上限、整组长度校验|
|`backend/apps/terminology/curd/terminology.py`|新增和编辑接入校验；编辑合并为一次提交；批量标准化保留来源信息|
|`backend/apps/terminology/models/terminology_model.py`|请求模型增加工作表和行号字段，仅用于导入诊断，不新增数据库列|
|`backend/apps/terminology/api/terminology.py`|读取Excel时记录原始行号，错误信息附带工作表和行号|

批量入口原本按组调用新增方法，成功组单独提交、失败组回滚，因此复用新增校验即可在超长组写入前拒绝。这里是实现说明，尚无混合Excel导入的现场验证证据。界面沿用现有错误提示，没有新增实时token计数器。

下一阶段应先处理现有超长解释、验证混合导入，再统一改造向量生成、重建存量向量并切换术语专用参数。重建后验证所有主术语和同义词都使用一致文本格式、维度正确，最后做工程回放与接口性能测试。后续进一步调参需要新的未参与调优样本。

## 管理员编写建议

同义词应表达同一业务概念，避免用泛化或时间含义不一致的句子扩大匹配范围。解释应优先写清适用范围、关键区分和计算口径，删除重复措辞，不能为缩短文本删除必要规则。通过率应保留大于等于60分、排除0分及空成绩、分母为有效成绩人数、分母为零不返回0%等已确认规则。每次更改解释或同义词都应执行固定回归样本。
