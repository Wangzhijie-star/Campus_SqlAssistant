# SQLBot 后端稳定性开发计划

记录日期：2026-09-11。状态：七项方向已确定，尚未实施。第一阶段进入幂等与链路推进设计。

## 目标与边界

围绕普通用户、已配置数据源的问数链路，提高重复请求、并发、超时、进程退出和下游故障时的可控性。未来 Java 算法学习平台可通过 HTTP API 接入；MCP 作为独立接入方式，不与嵌入助手绑定。

助手、嵌入页面和高级应用暂不扩大开发范围，不按 assistant 关键词删除共享代码。此前的召回实验暂停；SQL 示例重设计与 Excel 修改也暂停。

以下现状来自工作区源码静态检查，不代表对 Ubuntu 运行副本、所有插件、SDK 默认行为或部署网关完成了验证。

## 七项开发方向

|编号|方向|源码现状|计划交付|完成标准|
|---|---|---|---|---|
|1|幂等与持久化任务状态|接收问题后直接创建 ChatRecord、提交线程池；未见请求级唯一键与阶段版本约束|请求幂等契约、任务表、结果复用、受控状态转换、进程中断处理|同键同请求只有一个任务/记录；不同内容冲突；重复请求不推进业务状态；异常状态可查询|
|2|会话并发与执行权|已有 PostgreSQL advisory lock 工具用于后台单实例任务；普通提问未见会话串行化|同会话活跃任务约束、租约、执行代次、旧执行者拒绝提交|同会话不同请求不能同时有效推进；不同会话可并行；失去执行权的线程不能覆盖结果|
|3|容量、超时、熔断与恢复|问数线程池 max_workers=200；部分调用有超时；模型参数可传入 SDK|整轮截止时间、有界队列、模型/数据源并发预算、有限重试、分依赖熔断|依赖变慢不会无限积压；拒绝原因可观测；故障恢复后受控放量；不叠加无界重试|
|4|多级降级与人工兜底|存在局部异常处理、文本召回保留、SQL/数据/图表阶段划分|错误分类、部分成功响应、人工处理入口和恢复规则|图表失败保留真实数据；权限/安全失败停止；人工处理留审计并重新校验|
|5|Action 契约与上下文快照|模型生成 SQL/图表，Python 执行并保存；从文本提取 JSON；历史按轮数截取|严格输出结构、允许动作集合、确定性转换函数、版本化快照、上下文预算|未验证模型输出不能触发状态变更；快照能说明使用了哪些 schema、知识、权限和模型版本|
|6|短期与长期记忆|已保存聊天记录、模型消息、SQL/结果；有术语与 SQL 示例知识库|结构化会话事实、最近对话、可追溯摘要、长期知识审核/失效规则|摘要不覆盖用户确认；权限不从记忆恢复；无跨用户泄漏；模型答案不自动晋升为可信知识|
|7|安全审计与可观测性|已有权限、SQL 只读/危险语句检查、ChatLog、系统操作日志|统一请求/任务关联、审计事件、脱敏、保留策略、错误脱敏、指标与告警|阶段推进/重试/回放/人工处理可追踪；用户错误不泄漏内部 traceback；敏感数据访问受控|

## 实施顺序

1. 第一阶段：第1项为主体，同时纳入必要的第2项执行权约束与第7项审计字段。详见[幂等与链路推进设计](D:/SQLBot-main/项目学习文档/幂等与链路推进设计_AI-meeting对照.md)。
2. 第二阶段：完善第2、3项，包括会话并发、排队、整轮超时、熔断与故障恢复。
3. 第三阶段：第4项降级与人工入口，保留失败前已经验证的结果。
4. 第四阶段：第5项上下文快照和 Action 契约。
5. 第五阶段：先实现第6项短期治理，再建设长期记忆。
6. 第7项贯穿每个阶段，而非最终才补日志。

阶段编号不是要求一次性引入全部组件。优先用已有 PostgreSQL、SQLModel/SQLAlchemy 和 Python 服务结构，确有需求再增加 Redis、消息队列或工作流框架。

## 不可放宽的边界

- 幂等保护的是同一业务操作的有效提交，不承诺外部模型、只读查询在任何崩溃点都物理执行一次。
- 锁不等于幂等，缓存不等于持久化任务状态，日志不等于可恢复状态机。
- 多级降级不能绕过权限、只读约束或数据源隔离；不能用模型猜测替代失败查询。
- 缓存回放也要重新校验当前访问权限，明确历史结果时间。
- SQL/模型输出仍须验证。存进快照不自动使其成为可信事实。
- Java 接入与网页使用同一后端幂等和权限规则，不用管理员身份代理所有用户。

## 验证方式

每阶段分别检查正常路径、重复/并发路径、故障路径、权限边界与恢复行为。并发与事务测试必须使用真实 PostgreSQL；进程内 mock 或 SQLite 不能证明跨进程唯一约束和锁行为。

记录请求数、实际任务数、模型/查询调用次数、有效状态提交次数、回放次数、旧执行者拒绝次数、排队时间及失败分类。明确哪些是源码已实现、测试观察，哪些仍为待实现设计。
